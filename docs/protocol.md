# Backend ↔ Core protocol

Defined in [`api/proto/threavia/backend/v1`](../api/proto/threavia/backend/v1),
following specification sections 9 and 26. The Go bindings in `gen/` are
generated by `make generate` and are never edited by hand.

## Shape

One service, one bidirectional stream:

```proto
service BackendControl {
  rpc Connect(stream BackendToCore) returns (stream CoreToBackend);
}
```

Everything else is a `oneof` branch of those two envelopes. There are no
provider-specific RPCs, and no provider assumption in any message.

| Backend → Core | Core → Backend |
| --- | --- |
| `Hello` | `Welcome` |
| `Heartbeat` | `StartJob` |
| `StatusUpdate` | `CancelJob` |
| `QuotaReport` | |
| `ReconcileState` | `ValidationResolution` |
| `JobEvent` | `UserInputResolution` |
| `EphemeralJobEvent` | `JobInputNow` |
| `CommandResult` | `JobInputNext` |
| `CoreToolRequest` | `ReconcileInstruction` |
| `SkillInventory` | `EventAck` |
| `SkillFetchRequest` | `CoreToolResponse` |
| `WorkspaceDiff` | `SkillBundle` |
| `RepositoryStatus` | `UpdateJobPolicy` |
| | `WorkspaceDiffRequest` |
| | `RepositoryStatusRequest` |

## Session model and reasoning effort

Core persists each Session's model and effort preferences in PostgreSQL. Empty
preferences use backend defaults. A change applies when the next Job launches,
including a queued Job; NOW/NEXT messages retain the running Job's settings.

A backend advertising `FeatureFlags.model_selection` includes a
`Hello.model_catalog`: provider model ids, display names, the efforts each
model accepts, and defaults when known. Core exposes that catalog to both
clients and rejects unsupported choices. Legacy backends continue running
Sessions with default settings; explicit preferences are refused.

`StartJob.model` and `StartJob.effort` carry the configuration frozen at launch.
The backend applies it on fresh and resumed provider sessions and on every turn
within that Job. It must fail an unsupported configuration instead of silently
substituting a model. When known, `JobStarted.model` and `JobStarted.effort`
confirm the actual provider settings; Core retains them on the Job and in
completion/failure event payloads. Unknown settings stay absent.

Codex discovers models through app-server `model/list`. Claude advertises the
stable Sonnet, Opus and Haiku aliases and offers effort only when the installed
CLI advertises `--effort`. Catalogs are read at backend startup; restarting the
backend refreshes them. Session changes produce `session.model_changed` events
and audit entries, so open clients follow changes made on another device.
A connection also emits owner-scoped `backend.models_updated` with
`{backendInstanceId}`, prompting clients to refresh the announced catalog.

## Connection

The backend always dials Core; Core never needs inbound connectivity to a
laptop. The connection carries the backend credential as gRPC metadata:

```text
authorization: Bearer <backend credential>
```

Core resolves it to a BackendInstance before reading anything from the stream.
The credential is never logged, and provider credentials never travel on this
stream at all.

## Handshake

1. The backend sends `Hello` as the first message: protocol version, SDK,
   backend identity, instance name, capabilities, optional feature flags and
   capacity.
2. Core rejects a protocol version it does not speak with `FailedPrecondition`:
   the protocol version is the contractual compatibility boundary.
3. Core answers `Welcome` with a fresh `connection_id`, the resolved
   BackendInstance id and the heartbeat interval it expects.
4. The backend reports its `ReconcileState`, then replays any event Core has not
   acknowledged, then starts heartbeating.

A `Hello` sent again mid-stream is rejected with `InvalidArgument`.

The instance name in `Hello` replaces the stored one, so renaming a backend is a
change to its configuration and a restart, not a new registration. A name
another live backend of the same owner holds is logged and ignored: the old
name stays and the connection goes on.

## Quotas

`QuotaReport.snapshot` follows the HTTP `BackendQuotas` schema. Each instance
reports its own limits and thresholds, with stable window ids, optional usage,
provider status, resets and raw quota metadata. Missing values remain absent;
Core validates and stores a bounded snapshot and publishes the owner-scoped
`backend.quotas_updated` notification. Provider credentials never enter this
report. Older backends can omit it and clients show an unknown quota status.

Codex polls `account/rateLimits/read` every minute and forwards
`account/rateLimits/updated` notifications, including every family in
`rateLimitsByLimitId`. Window objects are discovered by their usage, duration
or reset fields; primary/secondary status-only windows remain supported. Names
combine the provider's limit name and model slug, falling back to the family id,
without model
aliases or assumptions about which special quotas an account should have.
Reading quotas never enables automatic reserve fallback.
API-key accounts report unsupported subscription quotas.
Claude polls its CLI `get_usage` control every minute without starting a model
turn, persisting a session or loading MCP servers. Every entry in the canonical
usage list is retained; legacy windows and scoped arrays are discovered by their
usage fields. Scoped identities include all dimensions, and labels use provider
names for models, surfaces and future scope dimensions. Explicit durations take
precedence over legacy period conventions. Both clients render the reported list
generically: adding a quota within these provider schemas needs no UI change.
Claude also forwards `rate_limit_event.rate_limit_info`,
including unified windows and provider thresholds. Threavia never reads OAuth
credentials or calls an independent Anthropic usage endpoint. Older CLI versions
that lack the usage control report the failure explicitly. Partial
notifications keep other windows; a failed poll preserves the last values and
observation date with an unavailable status.

## Connection lease

Only one connection is active per BackendInstance. A newly authenticated
connection receives a new `connection_id` and supersedes the previous one, which
is closed with `Aborted` and receives no further work.

On shutdown Core closes every connection with `Unavailable`; backends reconnect
with exponential backoff.

## Event identity

Three identifiers, each with one job:

| Identifier | Scope | Purpose |
| --- | --- | --- |
| `backend_event_id` | unique per BackendInstance | deduplication of at-least-once delivery |
| `backend_sequence` | monotonic per Job | ordering and replay-gap detection |
| global sequence | Core-wide | client cursor, assigned by Core on persistence |

A per-Job sequence is what lets unrelated concurrent Jobs stream without being
serialised against each other.

Core acknowledges persisted events with `EventAck` carrying
`through_backend_sequence`; only then may a backend drop them from its durable
buffer. Until the Core event pipeline is implemented, Core sends no
acknowledgement, so nothing is dropped.

`EphemeralJobEvent` is the exception: progress and "agent working" signals are
streamed for liveness and never persisted.

## Commands and results

A `CoreToBackend` message carrying a `command_id` expects a `CommandResult` with
the same id. A backend that cannot honour a command answers
`accepted: false` with an error code rather than silently ignoring it.

`ReconcileInstruction` carries the Core decision after a reconnection: replay
events from a sequence, reissue a cancellation, or abandon a Job. The rule is
the one of section 9: Core is the source of truth for desired logical state, the
backend is the source of truth for what actually happened locally.

A `ReconcileState` only speaks for the backend's own Runs: Core records the
`native_session_id` of a Run this BackendInstance executes, and ignores one
reported for any other Run. The id must also be a short token, without
whitespace and not starting with `-`, since it reaches the provider's command
line when the Run resumes; anything else is ignored too.

## Core Tools

An agent tool call travels as `CoreToolRequest` and is answered by
`CoreToolResponse`, correlated by `request_id`. The tools available for a Job are
described in the `ProjectContext` of `StartJob`, so a backend never hardcodes a
tool name.

A tool whose `CoreToolSpec.file_input` is set takes a file: that input property
is a path on the backend machine. The backend reads the file and sends its
content as `CoreToolRequest.file`, because Core never reaches a backend's disk.
It reads only within the Job's working directory and scratch directory, after
resolving links, never a file the Job's policy refuses to read, and up to
10 MiB. `artifact_publish` is such a tool: what an agent publishes becomes an
Artifact of its Session and an `artifact.created` event in the conversation.

A tool whose `CoreToolSpec.requires_validation` is set changes where future
Runs execute, and so what they may read without asking: `known_directory_register`,
`known_directory_bind` and `working_directory_set`. A backend that lets the
other Core Tools run without asking anyone still raises a `ValidationRequested`
before one of these, in every execution mode, `AUTONOMOUS` included, and runs it
only if the person approves: an agent must not be able to hand the next Run the
user's home directory on its own. A backend that does not know the field keeps
allowing these tools like the others, so the guarantee holds only from a backend
that reads it. What a backend does on its own behalf, such as recording where it
found a directory the person pointed it to, is not an agent's call and needs no
validation.

To remember a directory and attach the current Session to it, call
`known_directory_register` with `{name, path, useForSession: true}` (and optional
metadata or global scope). Core creates the KnownDirectory, its binding on the
calling backend and the Session's `workingDirectoryId` in one transaction.
Without that flag, registration only remembers the directory. For an existing
directory, use `working_directory_set({knownDirectoryId})`. These tools keep
their existing validation requirements.

Both attachment tools return `sessionId`, `knownDirectoryId` and
`effectiveFrom: "next_job"`. The current provider process retains its original
cwd; the agent uses the explicit requested path for work in that Job. Core
persists the attachment and resolves it into the next Job's ProjectContext.
The `working_directory.changed` event refreshes session lists, the Session
snapshot and repository state in both clients, and
`session.working_directory_changed` records the change in the audit.

Core also declares the session management tools described in
[Session management](session-management.md). `session_resolve_validation`
requires validation in every execution mode. Its input includes the worker's
original canonical permission payload and hash, so the approval appears in the
manager conversation. Core checks a matching human-approved receipt in the
manager's current Job before resolving the worker's request. It cannot approve
itself through a direct Core Tool call.

Core Tool requests run independently of the stream receive loop. A waiting
manager must not block worker events or heartbeats on the same connection;
responses remain correlated by request_id and use the connection's single
writer. Pending waits are cancelled when the control stream ends.

## Backend lifecycle

Core emits the persistent, owner-scoped `backend.status_changed` client event
after a connection, disconnection, or a changed status report. Its payload is
`{ backendInstanceId, operationalStatus, providerAuthState }`. Clients refresh
backend metadata, session lists, snapshots and attention; disconnection parks
unfinished jobs before the event is published. Repeated status reports and
heartbeat timestamps create no events. Superseded connection leases cannot
announce an offline state or park their replacement's jobs.

## Skills

`ProjectContext` names the Core-managed Project Skills of a Run — identity,
revision and bundle checksum, never content. A backend that has a revision
cached uses it; otherwise it sends `SkillFetchRequest` and Core answers with a
stream of `SkillBundle` chunks carrying the same `request_id`. The backend
verifies the checksum before unpacking, so a Skill cannot change identity in
transit.

`SkillInventory` travels the other way: the Skills that exist only on that
backend, as metadata. Core never fetches their content, which is what lets a
backend expose a Skill that only exists behind a corporate network, and what
lets a handoff report that another backend cannot run it (section 18).

The bundle is a tar.gz of the skill directory rooted at `SKILL.md`, with
supporting regular files and relative paths preserved. Executable bits are
normalized to `0644`; scripts need an installed interpreter. The
[Claude/Codex compatibility matrix](skills.md) describes native discovery,
supporting files and policy enforcement without changing this wire format.

Known-directory tools can list and register owner-global directories with
`scope: "global"`; the default scope is the current project. The project list
includes its owner's global directories. Updates, binding and forgetting accept
current-project or owner-global directory identifiers. The Core enforces owner
isolation and rejects deletion while any session uses the directory. These tools
only manage metadata and paths, never delete backend files.

## Working directory

The working directory stays on the backend. Core asks about it when someone
looks, and keeps nothing it hears back:

- `WorkspaceDiffRequest` asks for the diff of one file a `WorkspaceChanged`
  listed, between the two trees it named; the backend answers `WorkspaceDiff`.
- `RepositoryStatusRequest` asks where a Session's working directory stands in
  git — branch, distance from its upstream, what is not committed — and the
  backend answers `RepositoryStatus`. It reads without writing. With `fetch`,
  it fetches the remote first, never prompting for a credential; only the
  remote-tracking branches change, and a fetch that fails is said in
  `fetch_error` while the rest is the state as last known.

Both answers carry the request's `request_id`. They are optional: a backend
that does not implement them answers with an `UNSUPPORTED` error.

## Compatibility

`ProtocolVersion` is declared in `common.proto` and is the single source of truth
for both sides. Protobuf compatibility is preserved: fields are added, never
renumbered or repurposed. `make proto-breaking` checks this against the default branch.

## Prompt attachments

A backend that accepts attached files announces `FeatureFlags.prompt_attachments`
(`PROMPT_ATTACHMENTS` in the HTTP backend metadata). Core refuses attachment
messages on an older backend, rather than letting it silently ignore the files.

The HTTP start and message routes accept `artifactIds`: at most eight distinct
artifacts owned by the caller, from the same Project, totalling at most 3 MiB.
They require QUEUE delivery; text may be empty when files are present. The
`user.message` event keeps an `attachments` array of
`{ artifactId, filename, mimeType, size }` references. The bytes remain in object
storage and are fetched again when queued work is dispatched or replayed.

`StartJob.attachments` carries `PromptAttachment` entries with artifact id,
filename, MIME type and raw content. The total bound leaves room under the
default gRPC receive limit for the prompt and Project context. Backends place
files in their readable Run scratch directory and append their paths to the
prompt. Claude and Codex also receive PNG, JPEG, GIF and WebP as native image
content in the initial user message. Other media remain files for the agent's
available tools. A deleted attachment fails queued work explicitly.

User uploads emit a Project-scoped `artifact.created`, without adding a second
card to the conversation. Agent publications keep their existing Session-scoped
event. Removal emits Project-scoped `artifact.deleted` with `{ artifactId }`, so
all clients refresh their artifact lists. Downloads still use authenticated
attachment responses; clients render fetched bytes locally with their media
MIME type, and generated HTML stays isolated from the conversation.
